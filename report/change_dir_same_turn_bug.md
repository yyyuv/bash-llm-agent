## The same-turn `cd` bug: a follow-up command that ran in the wrong directory (Phase 6.5 / DECISIONS.md P6.5b, P6.5d)

Ready-to-insert source for the **Changing directories** section (a "what worked
and what didn't" case). Real data, `openai/gpt-4o-mini` native adapter, real zsh
with the shell wrapper installed. Absolute paths abbreviated to `.../project`.

`change_dir` writes the target directory to `~/.doit/cd_target_$DOIT_SESSION`; the
shell wrapper performs the real `cd` only **after** `doit` exits. That creates a
trap for any `run_command` issued in the **same** turn: the real `cd` hasn't
happened yet, so a bare command still runs in the old directory.

**The bug.** Request: *"go to the logs directory and list files in it"*. `change_dir`
resolved the path correctly, but the same-turn `ls` ran bare, in the OLD directory:

```
$ doit "go to the logs directory and list files in it"
· will cd to .../project/logs after this run
$ ls                          <- ran in the OLD cwd (.../project); the real cd hasn't happened
(the wrong directory's listing)
```

**The fix that did not work.** We added a paragraph to the system prompt explaining
that the real `cd` only takes effect after the process exits, and that a same-turn
command must target the resolved path. Model behaviour did not change — it kept
emitting a bare `ls`.

**The fix that worked.** We moved the warning out of the system prompt and into
`change_dir`'s own returned observation text — the tool result the model reads at
the exact moment it decides the next step ("you are NOT yet in the new directory;
a following command must target the resolved path explicitly"). The model then
pointed the command at the absolute path:

```
$ doit "go to the logs directory and list files in it"
· will cd to .../project/logs after this run
$ ls .../project/logs         <- now targets the resolved path -> correct listing
pwd: .../project/logs         (real shell cwd after doit exits)
```
*(logs/phase6_5/live_change_dir.txt, TEST 3)*

**A second, broader trigger (P6.5d).** In a real terminal, a request that only asked
to `cd` (*"go to the logs folder"*, nothing about listing) still made the model
volunteer an unrequested `ls` — which again ran before the real cd and showed the
wrong directory. The point-of-decision fix above only tells the model how to
target a follow-up, not whether to add one. We strengthened both the tool schema
and its observation text: do not add a follow-up command unless the user
explicitly asked to see/list the directory. Retest: no unrequested `ls`; explicit
"and list it" requests still list correctly.

**Confirmation the core mechanism works.** In a real terminal the zsh prompt itself
changed from `.../project %` to `.../logs %` after `doit` exited — the strongest
possible proof, since the prompt is generated by the live shell, not by `doit`.

**Lesson.** Same as the repeated-question bug: guidance placed at the point of
decision (the tool result the model is reading right now) changes behaviour where
the same guidance in a distant system-prompt paragraph does not.
